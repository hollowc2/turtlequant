## P0 — fix before trusting any shadow numbers

### 1. The fee rate is parsed wrong: fees are 10× too low (regression from `f9bd993`, today)

[`clob_execution.py:585-594`](../src/turtlequant/clob_execution.py) computes `rate = r × 10^-e` from the CLOB `fd` block.

The SDK (`py_clob_client_v2/fees.py`, `FeeDetails`) defines `e` as the **exponent applied to p(1−p)**: `fee = shares × r × (p(1−p))^e`.

Live CLOB response for every BTC/ETH market in today's scan:

```
fd = {'r': 0.07, 'e': 1, 'to': True}    base_fee = 1000
```

| Path | Rate the repo computes | Correct rate |
|---|---|---|
| `get_clob_market_info` (fd) — preferred since today | **0.007** | 0.07 |
| `get_fee_rate_bps` fallback | 0.10 (1000/10⁴) | 0.07 |

What this breaks:
- **Entries:** `executable_entry_price` includes about 1/10 of the real fee. At p=0.5 that inflates `ask_edge` by about 1.6pp, so borderline trades now pass that shouldn't.
- **Shadow/paper P&L:** fills record `fee_usd` 10× too low. Every shadow trade from now on looks better than it would live, including on the public performance page.
- **The diagnosis in `f9bd993` is partly wrong.** The old `base_fee` path overstated fees by 1.43× (0.10 vs 0.07), not 14×. The trade-frequency collapse was mostly caused by the 8.2pp RMSE haircut, which that commit correctly removed.
- **Exits disagree with each other.** The reprice-loop exit calls `get_market_fee_rate("", token_id)` ([`turtlequant_bot.py:526`](../scripts/turtlequant_bot.py)). The empty id skips market-info, so the rate is 0.10. The scan-loop exit passes `condition_id` and gets 0.007. The same position's exit fee depends on which loop closed it.
- `get_market_fee_rate(...) or DEFAULT_CRYPTO_TAKER_FEE_RATE` (lines 526, 765) turns a real 0.0 fee into 0.07. The entry path correctly uses `is not None`.

**Fix:**
- Return `(rate, exponent)` from the `fd` block.
- Compute `fee = shares × r × (p(1−p))^e` in `taker_fee`.
- Cache the result per condition_id.
- Store `condition_id` on `Position` so the reprice exit can look it up.
- Replace `or DEFAULT` with an explicit `None` check.
- Add a test fixture using the real `{'r': 0.07, 'e': 1}` shape.

### 2. Expired positions never settle

[`market_scanner.py:291-306`](../src/turtlequant/market_scanner.py) `fetch_resolution` reads `resolutionPrice`. That field does not exist on Gamma market objects, either in the list or at `/markets/{id}`. I checked resolved "Ethereum above 2,600 on September 23" markets: they show `closed: true`, `umaResolutionStatus: "resolved"`, `outcomePrices: ["1","0"]`, and no `resolutionPrice`. So it always returns `None`.

The result is that every position still open at expiry hits `[EXPIRED_PENDING]` and `continue` every 30s forever ([`turtlequant_bot.py:436-445`](../scripts/turtlequant_bot.py)).

Even if the field existed, `mark_pending_redemption` only sets a status. No code path ever removes a pending position or credits its payout to `current_nav`.

Consequences:
- **Exposure headroom leaks.** `kelly_size` and `expiry_exposure` add up `size_usd` for every position, pending ones included. Positions held to resolution eat into the 40% cap permanently, and entries eventually stop.
- **The track record is survivorship-biased.** Trades held to resolution never produce a `close` event, so they never reach realized P&L, the drawdown metrics, the Prometheus win rate, or the public performance page. A position that expires worthless, losing its whole stake, is invisible.
- **Log spam:** one WARNING per expired position every 30 seconds.

**Fix:**
- Resolve with `closed and umaResolutionStatus == "resolved"`, then take `outcomePrices[yes_index]`, matching the index the same way `_parse_raw` matches `outcomes`.
- In paper/shadow mode, settle right away: `close_position(exit_price=payout, exit_fee_usd=0, reason="resolved")`.
- In live mode, keep `pending_redemption` until the CTF `redeemPositions` is confirmed. See item 11.
- Leave pending positions out of the entry-exposure caps, or count them at payout value.

### 3. Parser false positives price non-price markets at ~100%

`_STRIKE_PAT` ([`market_parser.py:63`](../src/turtlequant/market_parser.py)) only understands `k`. The catch-all `_EUROPEAN_SIMPLE_RE` (line 101) matches *any* question containing an asset name and "above N". `_build_params` only checks that the strike is > 0. Reproduction (spot BTC 84k, σ=0.5, 60 days):

| Question | Parsed as | model_p |
|---|---|---|
| Will Bitcoin's market cap be above $2T by Dec 31? | european K=**2** | 1.000 |
| Will Bitcoin reach $1 million by 2030? | barrier K=**1** | 1.000 |
| Will Bitcoin hit $1.5M before 2030? | barrier K=**1.5** | 1.000 |
| Will Bitcoin dominance be above 60% on Dec 31? | european K=60 | 1.000 |
| Will BTC ETF inflows be above $500M on Oct 1? | european K=500 | 1.000 |
| Will the Bitcoin hashrate be above 1,000 EH/s…? | european K=1000 | 1.000 |
| Will Bitcoin reach $100k or dip to $70k first? | barrier K=100k | 0.370 (a race, not a touch) |
| Will ETH be below $2,000 on Dec 31? | unparsed (`EUROPEAN_PUT` is never produced) | — |

Any of these trading between 0.02 and 0.98 produces a signal with an edge up to about 0.9. That buys the full per-market cap, which is 10% of NAV. "Will Bitcoin reach $1M" markets are a real Polymarket staple.

**Fix:**
- Add a strike plausibility band against live spot, for example `0.25·S ≤ K ≤ 4·S`, and reject anything outside it.
- Support `M/B/T` and `million/billion` suffixes, so that a wrong strike gets rejected by the band instead of being mis-scaled.
- Keep a deny-list: `market cap`, `dominance`, `ETF`, `inflow`, `hashrate`, `first`, `before it`, `flip`, `between`, `or`.
- Remove `_EUROPEAN_SIMPLE_RE`, or limit it to the exact template Polymarket uses (`^<Asset> above <N> on <date>`).
- Add a `below … on <date>` → `EUROPEAN_PUT` template.
- Build a parser test table from real questions, including `unclassified_markets.jsonl`.

## P1 — correctness and strategy

### 4. Discovery does not reach the markets the strategy targets

- **Gamma ignores `tag_slug=crypto`** ([`market_scanner.py:133`](../src/turtlequant/market_scanner.py)). Page 0 of today's query returned NFL, the Fed, and the 2028 primaries. The scanner is really fetching "the top 500 markets on Polymarket by 24h volume". Crypto price markets only show up when they happen to rank that high, and long-dated ones rarely do.
- **The spread filter is relative** (`spread / price`, line 58 and line 325), with a 3% limit. A 1¢ spread on a 5¢ token counts as 20%, so tails and long-dated markets are filtered out. Live scan today: 500 fetched → 81 parsed → **24 passed, and none was more than 6 days from expiry.** For example, "BTC reach $130k by Dec 31" failed at 19% relative spread.
- The README describes a "long-dated (weeks–months)" strategy. In practice the bot is a daily/weekly trader.
- The executable-edge gate already accounts for the spread, so the relative filter adds nothing and blocks good markets.

**Fix:**
- Discover through `/events` using the crypto tag id or the known series slugs, and/or `end_date_min`.
- Replace the relative spread cap with an absolute one (for example ≤3¢), or rely only on executable edge.
- Log how many markets fall into each filter bucket in `scan_summary`.

### 5. Exit rules give away expected value

[`position_manager.py:336-359`](../src/turtlequant/position_manager.py):
- **`edge_decayed`** sells when `model − bid ≤ 0.4 × entry_edge`, while `model − bid` is still *positive*. The bot sells a token for less than its own model says it is worth, and pays the taker fee to do it. `time_cleanup` does the same inside 6 hours.
- **The comparison is asymmetric.** `edge_at_entry = model − avg_fill` is measured against the ask without the fee. `current_edge = model − bid` is measured against the bid. So `current_edge` starts about one spread below `entry_edge`. With the 5% threshold and 3% relative spread allowed, a position can be half-way to `edge_decayed` the moment it opens.
- **Suggestion:** exit when selling is +EV after fees: `bid − exit_fee ≥ model_p − margin`. Or exit when model inputs degrade, such as a vol-source fallback or a stale spot. Otherwise hold to resolution, which needs item 2 fixed. If capital recycling matters, make it an explicit opportunity-cost rule instead of an edge-decay heuristic.

### 6. The circuit breaker can latch on forever

[`risk_controls.py:60-78`](../src/turtlequant/risk_controls.py): after 3 `consecutive_failures`, entries stop. Only `record_success`, which runs only after a trade fills, resets the counter. The counter is saved to disk and survives restarts.

`record_failure` fires on any per-market exception, any reprice exception, and any failed exit ([`turtlequant_bot.py:543, 641, 653, 1131`](../scripts/turtlequant_bot.py)). An exit that keeps failing therefore halts entries until an exit happens to succeed. A sell with no bids is one example: it re-fails every 30s. So is one malformed market that throws on every scan.

**Fix:**
- Count broker failures separately from data-plane errors.
- Reset or decay the counter after N clean scans or after a set time.
- Alert when the halt fires (Prometheus plus Discord), and show `halt_reason` on the dashboard.

### 7. Pricing model gaps

- **No skew term for digitals.** `N(d2)` evaluated at the strike's IV ignores the `−vega·∂σ/∂K` term. For crypto smiles near the money, that term can be several percentage points, the same size as the 5% entry threshold. Derive `P(S_T>K) = −∂C/∂K` from a call spread on the interpolated smile instead ([`probability_engine.py:49`](../src/turtlequant/probability_engine.py)).
- **Spot plus a fixed 5% rate instead of the forward** ([`probability_engine.py:23`](../src/turtlequant/probability_engine.py)). Deribit options are priced on futures, and `get_book_summary_by_currency` already returns `underlying_price` per expiry. Use it as the forward and set drift = 0.
- **The IV surface has no age limit** ([`vol_surface.py:155-215`](../src/turtlequant/vol_surface.py)). If Deribit fails, the old points are kept and still labelled `"deribit"` indefinitely. Add a maximum age, after which the bot falls back or blocks entries. Store strikes and compute moneyness at query time: line 188 freezes it at the spot seen when the surface was fetched.
- **Calibration tests a different model.** `calibrate_turtlequant.py:91` uses 30-day realized vol, but the live bot trades on Deribit IV, which carries a variance risk premium. The Brier/RMSE gate therefore says nothing about the model that trades. It also doesn't test the actual hypothesis, which is "when model − market ≥ 5%, the model wins." The shadow `signal_evaluation` events joined with the item 2 resolutions are exactly the data needed for that test.

### 8. Partial closes over-charge the entry fee

[`position_manager.py:251-257`](../src/turtlequant/position_manager.py) charges `entry_fee_usd × close_ratio` but never reduces `entry_fee_usd`. Reproduction: a $1.75 entry fee closed in two halves is charged **$2.625**. Reduce the stored fee by the amount charged, or keep a per-token fee. `realized_exit_fees_usd` is tracked but never read.

### 9. `--dry-run` changes state

`execution_mode` becomes `"paper"` in dry-run mode ([`turtlequant_bot.py:350`](../scripts/turtlequant_bot.py)). Only order submission is guarded by `if not args.dry_run`. `close_position`, `record_realized_pnl`, `record_success` and `append_history` still run (lines 563-626 and 804-867), against the default state dir. The README says dry-run makes "no order or position state changes." Either skip all mutations, or require a separate `--state-dir` for dry-run.

### 10. Secrets exposure in compose

- The exporter mounts **`.:/app`**, the entire checkout including `.env` with `POLYMARKET_PRIVATE_KEY` ([`docker-compose.yml:72`](../docker-compose.yml) and `docker-compose.live.yml:24`). That same container runs `pip install prometheus_client requests numpy` with nothing pinned on **every start** (line 68). Any compromised package release gets read access to the wallet key. Mount only `src/` and `scripts/` read-only, and build a pinned image from `uv.lock`.
- The shadow bot receives `POLYMARKET_PRIVATE_KEY` (line 40), and `ExecutionClient` derives API credentials from it even in paper/shadow mode. Order books are public, so only pass keys when running `--live`.
- Deribit auth sends `client_secret` as a GET query string ([`vol_surface.py:129-139`](../src/turtlequant/vol_surface.py)). It is redacted in logs but can still end up in proxies. For public IV data, auth isn't needed at all.
- OPS.md records a past Deribit key leak in the monorepo history. The public performance page links to this repo, so confirm the keys were rotated and the extracted history doesn't include `crypto_up_or_down/docs/turtlequant_plan.md`. I couldn't check the history scan from this session.

## P2 — robustness and ops

### 11. Live path (currently hard-disabled at `turtlequant_bot.py:347`)
Fix these before re-enabling live mode:
- **A failed order leaves an unreconciled intent.** An intent is created, `submitted()` runs, the fill fails, and the code `continue`s without reconciling. On the next start, `reconcile_outstanding` finds a non-`matched` order, raises `ReconciliationError`, and **startup is blocked** (`order_reconciliation.py:43-50`). The same happens with a crash between `pending()` and `submitted()`, which leaves no `order_id`. Add terminal states (`failed` / `cancelled`) and write them in-process.
- **Ambiguous responses** (`pending_reconciliation`) are treated as plain failures while the bot keeps running. A BUY that actually filled isn't recorded, and the next scan can buy again. Block the market, or halt, until the intent is reconciled.
- **No redemption:** winning positions need a CTF `redeemPositions` call, or the pUSD stays on chain.
- **Reconciliation fee** uses `fee_rate_bps/1e4 × p(1−p)`. If trades report the base fee of 1000, that is 0.10 instead of 0.07.
- **The live override crash-loops.** `docker-compose.live.yml` plus `restart: unless-stopped` meets `sys.exit(1)`. OPS.md documents live steps that can't currently run.

### 12. Only YES is traded
Every trade is "buy YES when model > price". When model < price, the edge is in buying NO, and that side is ignored. On touch and barrier markets the well-known longshot bias usually overprices YES, so this is probably the larger half of the opportunity set. The scanner already parses `no_token_id`. Supporting NO means generalizing `Position` with an `outcome` field and flipping the probability.

### 13. Portfolio risk
- There is no per-asset or net-delta cap. "BTC above X" and "BTC reach Y" positions are all long BTC, and they share the same model error (vol level, skew). The per-expiry cap groups by calendar date only.
- Kelly sizing uses realized NAV only. Model uncertainty (the RMSE of about 5pp) isn't included. At minimum, shrink `model_p` toward the market price before sizing, rather than when gating.

### 14. Unbounded growth
- **History JSONL.** Each scan appends `scan_summary`, plus `signal_evaluation` and `shadow_quote` for every candidate, each with 10-level books, and each followed by an `fsync`. Roughly 50–100 MB/day with about 10 persistent candidates. Nothing rotates it. The exporter keeps **every event in memory** and rebuilds every group whenever a new line arrives, which is on every scrape (`grafana_exporter.py:249-330`). The performance page reads the whole file every hour. Split high-volume diagnostics into a separate, rotated file and keep trade events small.
- **The exporter's incremental reader** jumps to EOF even when the last line is only partly written, and drops it as a JSON error. It also doesn't notice when the file is truncated (`size < offset`).
- **The unclassified corpus** is appended every scan, without dedupe, to `./unclassified_markets.jsonl` ([`market_parser.py:119`](../src/turtlequant/market_parser.py)). In the container that path is `/app`, the writable layer rather than the state volume, so it grows until rebuild and is then lost. Dedupe it and write it to `STATE_DIR`.
- **`turtlequant_closed_position_pnl_usd`** has labels `idx, opened_at, closed_at, market_id, question`. That is one new series per trade, forever, which is a Prometheus cardinality problem.

### 15. Container and runtime
- The Dockerfile syncs with `--no-dev`, but the command is `uv run python …`. By default `uv run` re-syncs the default groups, dev included, so pytest and ruff are probably fetched at container start. Set `UV_NO_DEV=1` / `UV_FROZEN=1`, or invoke `python` directly.
- `uv:0.5.11` is about 18 months old. The exporter image is `python:3.12` while `requires-python >=3.13`.
- The Dockerfile's default `CMD` is `--paper` while compose uses `--shadow`. Pick one.

### 16. Main-loop details
- The stale-data gate never fires. `scan_started_at` is taken *after* `get_active_markets()` returns, so the prices are always older than the timestamp they're checked against ([`turtlequant_bot.py:657`](../scripts/turtlequant_bot.py)).
- `recently_closed` (the 2-hour cooldown) lives only in memory, so a restart right after an exit allows immediate re-entry.
- `[ENTRY_HALTED]` is logged at WARNING once per market per scan while halted. Log it once per scan.
- The reprice loop fetches Gamma `lastTradePrice` (the fields `resolutionPrice` and `price` don't exist) and uses it as *both* sides of the fallback synthetic book. A stale last trade then becomes the exit price.
- Everything runs serially: book and fee lookups happen per candidate, with retries and backoff, so the 30s reprice waits behind a slow scan.

## P3 — maintainability, tests, docs

### 17. Structure
- `main()` is about 900 lines. The exit block (order, history, close, notify) appears twice, almost identical: lines 505-626 and 736-868. The two copies have already drifted (fee lookup, fallback prices). Pull out a `Trader` with `evaluate_exit(pos, quote)`, `try_enter(market)` and `settle(pos)`, and make decisions pure functions of `(state, quote, model)` so they can be unit-tested.
- `fetch_spot` is dead code. The `MarketParams` import is inside the loop. `ASSET_TO_SYMBOL` is defined in 3 files and `RISK_FREE_RATE` in 2.
- Paper and shadow differ only in a status string: `shadow_quote` events are written in both modes. Merge them, or make shadow actually different.
- Several strategy constants are hard-coded instead of configurable: 0.4 decay, 6h / 5% cleanup, 0.02/0.98 bounds, 2h cooldown, 10/15/40% caps.

### 18. Tests
- The tests that cover the two worst bugs use fixtures in the *wrong* API shapes (`{"resolutionPrice": "1"}` in `test_market_scanner.py:87`, and no `fd` exponent fixture), so the P0s pass. Record real Gamma/CLOB responses as fixtures and use them as contract tests.
- There is no test of the main loop. `test_market_parser.py` has 2 cases. There is no CI: add a GitHub Action running `ruff` and `pytest`.

### 19. Doc and config drift
- The README says Binance falls back "Bybit → OKX → Gate.io". In fact only a 451 response falls back, and only to OKX.
- The README says "long-dated" (see item 4). It also says dry-run makes "no state changes" (see item 9).
- The exporter's `TAKER_FEE_RATE = 0.003` flat fee doesn't match the bot's `r·p(1−p)`.
- The `DISCORD_CHART_INTERVAL` default is `4h` in code and `1h` in compose.
